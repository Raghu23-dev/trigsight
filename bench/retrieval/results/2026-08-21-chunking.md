# The chunking hypothesis was wrong

**Date:** 2026-08-21 · **Change:** paragraph-aware chunking, `MAX_CHARS` 1400 → 700
**Result:** **no measurable effect.** recall@5 and MRR identical to four decimal places.

## What was predicted

A recorded hypothesis from the earlier retrieval work:

> The missed query is a chunking problem, not an embedding problem. A 1,340-character chunk
> averages five topics into one vector, so the vector points at none of them. Split on paragraph
> boundaries within a section and re-measure.

The diagnosis of the *chunk* was correct. `work/context-compaction#3` was 1,340 characters and
packed four distinct topics — structural digests, atomic writes, an advisory lock, and threshold
calibration. The answer to *"what happens when two compactions run at once"* was one sentence
inside it.

The prediction about the *fix* was wrong.

## What the change did

| | Chunks | recall@5 | MRR |
|---|---|---|---|
| Before — 1400 chars, sentence packing | 47 | 0.967 | 0.889 |
| After — 700 chars, paragraph-aware | 60 | **0.967** | **0.889** |

Identical. The same single query misses either way.

A real bug was fixed in passing. `splitLong` was documented as splitting "on paragraph
boundaries", but `renderToText` collapses every run of whitespace to a single space *before* it
was called — so the blank lines marking paragraphs were already gone. The function could only ever
fall back to packing sentences to a character limit. **The paragraph split it claimed to perform
was structurally impossible.** Chunks are now genuinely cut on paragraphs, and the target chunk
went from 1,340 characters covering four topics to 650 covering one.

It changed nothing measurable.

## Why the query still misses

The chunk is now correct and focused. It still cannot be retrieved, and the reason is vocabulary:

```
query:  "what happens when two compactions run at once"
chunk:  "a transaction-scoped advisory lock serialises concurrent attempts,
         and the loser declines rather than queueing"
```

**Not one content word in common.** "At once" versus "concurrent"; "two compactions" versus
"attempts". Lexical retrieval scores it at zero by construction. And the embedding — which should
bridge exactly this gap — ranks it **13th** on a 60-chunk corpus.

Isolating the variable: with the chunking reverted, and again with the three new project documents
removed, the numbers do not move. **0.967 / 0.889 in all four configurations.** The miss is not
caused by chunk size and not caused by corpus growth.

## The correction that matters

The earlier note said real embeddings would not fix this. That was recorded when the only backend
available was the local trigram stand-in, and it was measuring the stand-in:

| Backend | recall@5 | MRR |
|---|---|---|
| lexical only | 0.933 | 0.784 |
| hybrid, local trigram stand-in | 0.900 | 0.850 |
| **hybrid, real embeddings** | **0.967** | **0.889** |

Real embeddings *were* the improvement — **+3.4 points of recall and +10.5 of MRR** over
lexical-only — and the credit was previously assigned to the wrong thing. Under the stand-in,
hybrid retrieval scored *worse* than lexical alone, which is exactly what a non-semantic
placeholder should do and precisely why a number from it must not be reported as embedding-model
performance.

## Why the change was kept anyway

It does not improve the metric. Three reasons it stayed:

1. **A function that lies about what it does is a latent bug.** The next person to raise
   `MAX_CHARS` would reasonably expect paragraph boundaries to be respected. They were not.
2. **Chunks that cover one topic are cheaper to cite.** The citation gate requires a passage to
   sit inside one block element, and a chunk spanning four topics invites quoting across them.
3. **It costs nothing.** 60 chunks instead of 47, no latency change, no budget change.

Keeping it is a judgement call, not a result, and it is labelled as such. Had it *worsened* the
metric it would have been reverted.

## What would actually fix the miss

A query-side rewrite — expanding "at once" to include "concurrent", "simultaneous", "in parallel"
before retrieval. That is a different mechanism from chunking and belongs to its own measurement,
with its own risk: query expansion that fires on the wrong synonym degrades every other query.

**One miss in thirty is being published rather than engineered away.** The threshold is ≥0.85 and
the result is 0.967. Adding query expansion to chase 1.000 on a 30-query golden set would be
tuning to the test.

## Reproduce

```bash
tsx bench/retrieval/index-upstash.ts   # reindex after any chunker change
tsx bench/retrieval/eval.ts
```

The reindex is not optional. The vector store holds embeddings of the *old* chunk boundaries, so
evaluating a chunker change without reindexing measures stale data against new code — which the
first run of this comparison did, and which is why the trigram row moved while the embedding row
did not.
